### Q1 — The OAuth `state` parameter and CSRF

*What is the `state` parameter in the OAuth Authorization Code flow?  What
specific attack does it prevent, and what would happen if Auth.js omitted it?
Walk through the attack scenario step by step.*

**Your answer:**

<!-- Write here -->

---

**Model answer (read AFTER filling yours in):**

<details>
<summary>Reveal model answer</summary>

The `state` parameter is a random, unguessable nonce generated by Auth.js
when the user initiates the OAuth flow.  Auth.js stores it in a short-lived
cookie and appends it to the authorization URL sent to GitHub.  When GitHub
redirects back to the callback URL, it includes the same `state` value.
Auth.js verifies that the returned `state` matches the cookie — if they
differ, the flow is aborted.

Without `state`, an attacker could execute a **CSRF on the OAuth callback**:

1. The attacker visits the OAuth authorization URL for their own GitHub
   account, generating a valid auth code.
2. Before completing the flow, the attacker aborts (or starts but does not
   finish the redirect).
3. The attacker crafts a link to the callback URL with their own code:
   `/c23-oauth-authjs/api/auth/callback/github?code=ATTACKER_CODE`
4. The attacker tricks a victim into visiting this link (e.g. in an email
   or an `<img src="...">` tag).
5. The victim's browser visits the callback URL, which exchanges ATTACKER_CODE
   for an access token, fetches the attacker's GitHub profile, and creates a
   session — signing the victim in as the attacker (account linking CSRF).
6. The attacker can now access the victim's account (if account linking is
   allowed) or the victim is unknowingly using the attacker's identity.

With `state`: step 5 fails because the victim's browser has no cookie
matching the `state` that was in the attacker's authorization URL.

</details>

### Q2 — JWT session vs. database session: the revocation trade-off

*Auth.js uses JWT strategy (no database) in this challenge.  A user changes
their password and wants all their sessions terminated immediately.  Can you
do this with a JWT-only session?  What architectural change would enable
immediate revocation, and what is the cost?*

**Your answer:**

<!-- Write here -->

---

**Model answer (read AFTER filling yours in):**

<details>
<summary>Reveal model answer</summary>

No — you cannot immediately revoke a JWT-only session.  The JWT is a
self-contained, stateless token.  Auth.js verifies it by checking the
signature and expiry, not by querying a database.  Even if you "delete" the
session by clearing the cookie, an attacker who already copied the raw token
value (e.g. from an XSS exfiltration) still holds a cryptographically valid
token that Auth.js will accept until `exp`.

To enable immediate revocation you need **shared state** — either:

1. **Database session adapter** (Auth.js built-in): the JWT cookie holds only
   a session ID.  Every request queries the database to verify the session row
   exists.  Logout = delete the DB row = instant revocation.  Cost: a DB read
   on every request; requires a persistent session store that scales with traffic.

2. **Token blocklist** (hybrid approach): keep JWT strategy but maintain a
   Redis set of revoked `jti` (JWT ID) values.  On every request, check the
   blocklist.  Cost: a Redis lookup on every request; blocklist entries must
   be pruned after they exceed the token's max lifetime.

3. **Short expiry + refresh tokens**: issue JWTs with very short lifetimes
   (e.g. 5 minutes) and a separate long-lived refresh token stored in the
   database.  After revoking the refresh token, the JWT becomes invalid within
   minutes.  Cost: complexity of the refresh token rotation flow.

The JWT strategy is appropriate when the security model can tolerate a window
of access after logout (e.g. internal tools) or when the session data changes
infrequently.  For user-facing apps that need "sign out everywhere", use a
database adapter.

</details>

### Q3 — Auth.js JWE vs. C01 JWS: encryption vs. signing

*Auth.js stores its session as a JWE (encrypted JWT).  C01 stores its session
as a JWS (signed JWT, payload is base64url-encoded and readable).  What is the
difference in security properties?  When would you choose JWE over JWS?*

**Your answer:**

<!-- Write here -->

---

**Model answer (read AFTER filling yours in):**

<details>
<summary>Reveal model answer</summary>

**JWS (JSON Web Signature):** The payload is base64url-encoded and can be
decoded by anyone (including the browser, the user, or an attacker who sees
the cookie in network traffic or a log file).  The signature proves the server
issued the token and that it has not been tampered with, but it provides no
confidentiality.  If you `atob()` the middle segment of a C01 token, you can
read the user's email, role, and expiry time.

**JWE (JSON Web Encryption):** The payload is encrypted.  Even if an attacker
intercepts the raw token, they cannot read what is inside it without the
server's private key (or shared secret).  Auth.js uses AES-256-GCM with a
key derived from `AUTH_SECRET`.

**When to choose JWE:** when the token payload contains sensitive data that
must not be visible even if the cookie is intercepted or logged — for example,
access tokens, internal user IDs, privilege flags, or any PII you do not want
exposed in server access logs.

**When JWS is sufficient:** when the payload contains only non-sensitive
identifiers (user ID, email, role) and you trust that `httpOnly` + TLS will
prevent the cookie from being read by scripts or network observers.  For many
applications, JWS is acceptable — the secrecy of the payload is not the
primary security property (integrity/authenticity is).

In practice Auth.js defaults to JWE (encryption) as a conservative choice.
C01 uses JWS intentionally so learners can inspect the token payload and
understand its structure.

</details>

### Q4 — `basePath` isolation: why not use the default `/api/auth`?

*This challenge sets `basePath: "/c23-oauth-authjs/api/auth"` in the Auth.js
config instead of the default `/api/auth`.  What problem does this solve?
What would break if you left it at the default?*

**Your answer:**

<!-- Write here -->

---

**Model answer (read AFTER filling yours in):**

<details>
<summary>Reveal model answer</summary>

The default Auth.js `basePath` is `/api/auth`.  This app might have multiple
Auth.js instances, or an existing `/api/auth` route used by a different part
of the app.  If two different Auth.js configs both mounted at `/api/auth`:

1. **Route collision:** Next.js would fail to build (two route handlers at
   the same path) or one would shadow the other at runtime.
2. **Cookie collision:** Auth.js cookies (e.g. `authjs.session-token`,
   `authjs.csrf-token`) would be shared between configs, causing one config's
   logout to clear the other's session, or CSRF tokens to be validated by the
   wrong handler.
3. **Redirect collisions:** The default sign-in page redirect
   (`/api/auth/signin`) would serve whichever handler happened to win — the
   wrong one for the other challenge.

By setting `basePath: "/c23-oauth-authjs/api/auth"`, this challenge:
- Mounts its route handler under a unique path (the `[...nextauth]/route.ts`
  file lives there).
- Issues cookies with names scoped to that path (or at least distinct from
  a default-path instance).
- Issues sign-in/out URLs pointing to the correct handler.
- Remains completely isolated from any other auth configuration in the app.

The `SessionProvider` in `SessionProviderWrapper.tsx` must also set
`basePath` to the same value so `next-auth/react`'s `signIn()` and
`signOut()` functions know which endpoints to call.

</details>

### Q5 — Credentials provider vs. OAuth: CSRF protection differences

*The Credentials provider and the GitHub OAuth provider protect against CSRF
differently.  Explain the mechanism used by each.  Which provides stronger
CSRF guarantees, and why?*

**Your answer:**

<!-- Write here -->

---

**Model answer (read AFTER filling yours in):**

<details>
<summary>Reveal model answer</summary>

**Credentials provider:** Auth.js uses a **double-submit cookie** pattern for
CSRF protection.  When the user loads the sign-in page, Auth.js generates a
CSRF token and stores it in a `__Host-authjs.csrf-token` cookie.  The
sign-in form must POST this token in the request body.  Auth.js verifies that
the body value matches the cookie value.  An attacker making a cross-origin
POST cannot read the cookie (same-origin policy) and therefore cannot include
the matching CSRF token in the body — the request is rejected.

**GitHub OAuth provider:** Auth.js uses the **`state` nonce** mechanism
described in Q1 — a random value stored in a cookie and sent to the provider,
then verified on the callback.  This is an OAuth-specific CSRF mechanism that
protects the entire OAuth flow (not just the sign-in form).

**Which is stronger?** Both mechanisms are industry-standard and correct.
The OAuth `state` mechanism provides an additional guarantee that the
credential flow lacks: it prevents an attacker from forcing a victim to
complete the attacker's OAuth flow (the account-linking CSRF attack).  The
Credentials provider does not have an equivalent risk because it does not
involve an external provider's redirect.

In practice, the primary CSRF risk for OAuth is the callback CSRF (Q1) —
the `state` nonce is the right defence for that.  The Credentials CSRF token
protects the POST-to-sign-in action.  Auth.js handles both correctly.

</details>

# Challenge Spec — Real OAuth with Auth.js (next-auth v5)

> **File:** `app/(challenges)/c23-oauth-authjs/_meta/spec.md`

## Learning Goal

This challenge teaches the OAuth 2.0 Authorization Code flow end-to-end,
using Auth.js (next-auth v5) as the framework layer.  You will understand how
Auth.js manages the OAuth handshake, why the `state` parameter is critical for
CSRF defence, and how JWT sessions differ from database sessions — all while
seeing the parallel with the hand-rolled `jose` session you built in C01.

---

## Background

### The OAuth 2.0 Authorization Code Flow

OAuth 2.0 is a delegation protocol — it lets a user authorize a third-party
application (your app) to act on their behalf with a provider (e.g. GitHub),
without ever sharing their provider credentials with your app.

The Authorization Code flow — the one Auth.js uses — works as follows:

1. **Redirect to provider** — Your app sends the browser to GitHub's
   authorization endpoint:
   ```
   https://github.com/login/oauth/authorize
     ?client_id=<YOUR_APP_ID>
     &redirect_uri=https://yourapp.com/api/auth/callback/github
     &scope=read:user user:email
     &state=<RANDOM_NONCE>
     &response_type=code
   ```
   The `state` parameter is a random, unpredictable string generated by
   Auth.js and stored in a short-lived cookie in the user's browser.

2. **User consent at GitHub** — GitHub shows the user a permissions screen.
   If they approve, GitHub redirects back to your callback URL with:
   ```
   /api/auth/callback/github?code=<AUTH_CODE>&state=<SAME_NONCE>
   ```

3. **CSRF check (state verification)** — Auth.js reads the `state` from the
   URL query string and compares it to the value stored in the cookie.  If
   they differ, the flow is aborted.  This is the CSRF defence: an attacker
   who tricks you into visiting a crafted callback URL cannot know the nonce
   value that was stored in YOUR browser's cookie.

4. **Code exchange (server-to-server)** — Auth.js sends a POST from your
   server to GitHub's token endpoint:
   ```
   POST https://github.com/login/oauth/access_token
     client_id, client_secret, code, redirect_uri
   ```
   GitHub responds with an `access_token`.  The auth code is single-use and
   short-lived (seconds to minutes); the access token grants API access.

5. **Profile fetch** — Auth.js calls GitHub's `/user` API with the access
   token to retrieve the user's profile (name, email, avatar URL).

6. **Session creation** — Auth.js calls the `jwt` callback, builds a signed
   and encrypted JWE (JSON Web Encryption), and writes it to a `httpOnly`,
   `sameSite=lax` session cookie.  The browser is redirected to the original
   destination page.

### The `state` Parameter and CSRF

Without the `state` parameter, an attacker could:
1. Start an OAuth flow themselves (visiting the authorization URL).
2. Abort before they complete it (stop before the callback).
3. Trick a victim into visiting the callback URL (e.g. embed it as an image
   or link).
4. The victim's browser would complete the attacker's OAuth flow — linking
   the attacker's provider account to the victim's app account (account
   linking CSRF) or signing the victim in as the attacker.

The `state` nonce breaks this because step 3 fails: the victim's browser has
no cookie matching the `state` from the attacker's flow.

### JWT Sessions vs. Database Sessions

Auth.js supports two session strategies:

| | JWT Session (this challenge) | Database Session (with an Adapter) |
|---|---|---|
| Session storage | Signed+encrypted JWE cookie | Cookie holds only a session ID |
| Per-request DB call | None | Yes — DB lookup on every request |
| Revocation | Only at cookie expiry | Immediate — delete the DB row |
| Horizontal scaling | Trivial (stateless) | Requires shared session store |
| Best for | Stateless APIs, edge deployments | Apps needing instant logout or audit |

The JWT in Auth.js is a **JWE** (encrypted), unlike the C01 `jose` session
which is a **JWS** (signed but readable).  Both use `httpOnly` and `sameSite`
cookies.

### How This Differs from C01 (Hand-Rolled `jose` Session)

| Aspect | C01 (`jose` + `lib/auth`) | C23 (Auth.js) |
|---|---|---|
| Token type | JWS (signed, payload readable) | JWE (encrypted, payload opaque) |
| CSRF protection | Manual if needed | Built-in (`state` nonce + CSRF cookie) |
| OAuth support | None | First-class (20+ providers) |
| Provider integration | DIY | Auth.js fetches profile, handles callback |
| Session callbacks | Custom code in `getSession` | `jwt` and `session` callbacks |
| Cookie management | Manual (`setSession`, `destroySession`) | Automatic |
| Collision | `nextmart_session` cookie | `authjs.session-token` cookie (different name) |

Both systems coexist in this app: C01's `nextmart_session` and Auth.js's
`authjs.session-token` are independent cookies using different secrets.

## Setup

### Credentials Provider (zero external setup)

The challenge ships a Credentials provider that accepts any of the seeded
`lib/data` user emails with any password.  No `.env.local` changes needed.

Demo users:
- `seller@nextmart.dev` (role: seller)
- `buyer1@nextmart.dev` (role: buyer)
- `buyer2@nextmart.dev` (role: buyer)

### GitHub OAuth Provider (optional — demonstrates real OAuth)

1. Go to https://github.com/settings/applications/new
2. Set **Homepage URL**: `http://localhost:3000`
3. Set **Authorization callback URL**:
   `http://localhost:3000/c23-oauth-authjs/api/auth/callback/github`
4. Click **Register application**.
5. Copy the **Client ID** and generate a **Client Secret**.
6. In `.env.local`:
   ```
   AUTH_GITHUB_ID=<your-client-id>
   AUTH_GITHUB_SECRET=<your-client-secret>
   ```
7. In `_lib/auth-config.ts`, uncomment the `import GitHub` line and the
   `GitHub({})` provider entry.
8. Restart the dev server.

## Acceptance Criteria

- [ ] Signing in with a Credentials demo user establishes an Auth.js JWT
  session and the session panel shows the user's name, email, and role.
- [ ] Visiting `/c23-oauth-authjs/protected` without a session redirects to
  `/c23-oauth-authjs`; with a session, it shows the protected content.
- [ ] Signing out clears the Auth.js session cookie; the panel shows
  "No active session".
- [ ] The GitHub OAuth provider is scaffolded and documented; adding
  `AUTH_GITHUB_ID` + `AUTH_GITHUB_SECRET` to `.env.local` and uncommenting
  the provider block enables the full OAuth flow without further code changes.
- [ ] `npx tsc --noEmit` passes with no errors.
- [ ] No `export const dynamic`, `export const runtime`, or
  `export const fetchCache` directives appear on any page in this challenge
  (incompatible with `cacheComponents: true`).
- [ ] Dynamic session reads (`auth()`) happen inside `<Suspense>` boundaries.
- [ ] The challenge appears in the challenge index (discoverable via the
  registry reading `challenge.config.json`).

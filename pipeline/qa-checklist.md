## Repo Build and Static Analysis

🔴 Repo builds successfully against the pinned Next.js version
  Scenario    : Run `next build` (or `npm run build`) in the repository root with the exact Next.js version declared in package.json. Do not allow any implicit upgrade.
  Pass if     : Build exits 0, produces a .next/ directory, and no "Module not found" or framework-API errors appear in stdout.
  Fail if     : Build exits non-zero for any reason, or the build succeeds only against a different Next.js version than the one pinned in package.json.
  Automatable : yes
  @critical

🔴 TypeScript typecheck passes across the entire repo with no errors
  Scenario    : Run `tsc --noEmit` (or `npm run typecheck`) from the root. All source files — app/, labs/, lib/, components/ — must be covered.
  Pass if     : tsc exits 0 with zero errors reported.
  Fail if     : tsc exits non-zero, or any "error TS" lines appear in output. "any"-escape hacks that mask real errors also count as a fail if they are not pre-approved suppressions.
  Automatable : yes
  @critical

🔴 ESLint passes across the entire repo with no errors
  Scenario    : Run `npm run lint` from the root against all source directories.
  Pass if     : Lint exits 0. Zero errors (warnings acceptable if they are pre-existing and documented).
  Fail if     : Lint exits non-zero, or any "error" severity findings appear.
  Automatable : yes
  @critical

🟡 No new TypeScript `any` casts introduced relative to the main branch baseline
  Scenario    : Diff the number of `as any` and `: any` occurrences between HEAD and the base branch.
  Pass if     : Count is equal to or lower than baseline.
  Fail if     : Count increases without a documented reason in the PR description.
  Automatable : yes
  @functional

## Authentication Gating — Middleware / proxy.ts

🔴 Unauthenticated requests to /account are blocked and redirected to login
  Scenario    : Make an HTTP GET request to /account (or any sub-path under /account) without a valid session token. Use both a bare fetch (no cookies) and a request with a tampered/expired cookie.
  Pass if     : Both requests receive a redirect (HTTP 3xx) to the login page, or a 401/403 response. The /account page HTML is never returned.
  Fail if     : Either unauthenticated request receives the /account page content with HTTP 200, or the middleware silently falls through.
  Automatable : yes (Playwright + API-level fetch)
  @critical

🔴 A forged or tampered session cookie is rejected by the auth middleware
  Scenario    : Construct a cookie that looks like a valid session token but is signed with a different secret (or has the payload altered). Send this cookie to /account.
  Pass if     : The middleware detects the invalid signature and redirects to login.
  Fail if     : The tampered cookie is accepted and the user lands on /account.
  Automatable : partial (requires a test utility that generates forged tokens; E2E feasible with a helper fixture)
  @critical

🔴 The C12 Server Action security reference solution rejects an unauthorized mutation
  Scenario    : Call the Server Action from C12 directly (via a raw POST to the action endpoint, bypassing the UI) without a valid session. Also attempt with a valid session belonging to a user who does not own the resource being mutated.
  Pass if     : The Server Action returns an error/unauthorized response in both cases. The mutation does NOT occur in the backing data store.
  Fail if     : Either unauthorized call succeeds and the mutation is applied, or the action relies solely on the UI being absent rather than server-side authorization.
  Automatable : partial (direct POST to Server Action endpoint is automatable; ownership check needs a second test-user fixture)
  @critical

🟡 Authenticated users can access /account without being redirected
  Scenario    : Sign in with a valid test-user credential, then navigate to /account.
  Pass if     : The page renders with HTTP 200 and the correct user-specific content is visible.
  Fail if     : A valid session triggers a redirect loop, a 401, or a blank page.
  Automatable : yes (Playwright)
  @functional

🟡 Login page itself is publicly accessible without authentication
  Scenario    : Request /login (or the configured login path) with no session cookie.
  Pass if     : HTTP 200, login form renders.
  Fail if     : Redirect loop or 403/500.
  Automatable : yes
  @functional

## Server-Only Secret Isolation

🔴 Reference solutions do not expose server-only environment variables in the client bundle
  Scenario    : Run `next build`, then inspect the generated client JS chunks under .next/static/chunks/ for any string matching the patterns of known server-side env var names (e.g. DATABASE_URL, SECRET_KEY, private API keys). Also run `NEXT_PUBLIC_`-prefixed variables through a positive check to confirm only intended variables are present client-side.
  Pass if     : No server-only secret strings appear in any client chunk. `server-only` import guards are present in all lib/ files that touch secrets.
  Fail if     : Any server-only secret value (or recognisable prefix) appears in a client bundle chunk, or a `server-only` guard is missing from a lib file that accesses process.env secrets.
  Automatable : partial (grep on built output is automatable; manual confirmation of the import-guard pattern is recommended)
  @critical

## PPR / cacheComponents — Product Page Rendering

🔴 The PPR product page renders its static shell without blocking on dynamic holes at first paint
  Scenario    : Navigate to the PPR-enabled product page (the Nextmart storefront product detail route). Observe the initial HTML response.
  Pass if     : The static shell (product title, image, description) is present in the initial HTML response with no `<Suspense>` fallback content visible in the source. The dynamic sections (stock count, personalised recommendations) are absent from the initial HTML and load asynchronously.
  Fail if     : The entire page is blocked until all dynamic data resolves (i.e., no meaningful static shell in the initial response), or `cacheComponents` is absent from the config and the page falls back to fully-dynamic SSR without explanation in the lab notes.
  Automatable : partial (Playwright can capture initial HTML before hydration; confirming the exact PPR boundary requires a visual or source inspection step)
  @critical

🟡 The PPR product page's dynamic holes fill in within an acceptable timeout after initial paint
  Scenario    : Load the PPR product page and measure the time from first paint to the dynamic sections becoming visible.
  Pass if     : Dynamic sections resolve and render within 3 seconds under local dev conditions.
  Fail if     : Dynamic sections never render, render with visible errors, or block the page for more than 5 seconds.
  Automatable : yes (Playwright with `waitForSelector`)
  @functional

## Intercepting Routes — Modal Navigation

🔴 The intercepting-route modal opens correctly via in-app soft navigation
  Scenario    : From the product listing page, click a product card that is wired to an intercepting route. Verify that the URL updates to the product detail path while the listing page background remains visible.
  Pass if     : The URL changes to the product detail path, the modal overlay renders on top of the listing page, and the listing page is still visible in the background.
  Fail if     : Navigation performs a full page reload to the detail page instead of showing the modal, or the modal renders with broken layout/no content.
  Automatable : yes (Playwright)
  @critical

🔴 The intercepting-route URL deep-links and refreshes to the full page, not the modal
  Scenario    : Copy the product detail URL from the modal navigation scenario above. Open it in a new browser tab (or perform a hard refresh on the modal URL).
  Pass if     : The product detail page renders as a full standalone page (not a modal overlay). The page has all expected content.
  Fail if     : The hard-refresh URL renders the modal UI within an empty page, or 404s, or throws a render error.
  Automatable : yes (Playwright — open URL directly without prior navigation)
  @critical

## Cache Invalidation — revalidateTag / revalidatePath

🔴 revalidateTag / revalidatePath actually invalidates the cache after a write
  Scenario    : (a) Load a cached page/data segment and capture the rendered value. (b) Trigger a Server Action or Route Handler that mutates the backing data and calls revalidateTag (with the correct two-argument form per Next.js 16) or revalidatePath. (c) Reload the page.
  Pass if     : The reloaded page reflects the updated data. The stale cached value is no longer served.
  Fail if     : The page still shows the pre-mutation cached value after a reload, or the revalidation call throws a runtime error (e.g., because the one-argument legacy form was used instead of the two-argument form).
  Automatable : partial (Playwright can verify the UI update; confirming the correct API call form requires a code-level check or runtime log inspection)
  @critical

🟡 The legacy four-cache model and migration challenge (C09) produces both a working pre-v16 variant and a working v16 variant
  Scenario    : Build and run the C09 reference solution. Verify that the v15-style fetch cache example (fetch with cache options) and the v16-style 'use cache' example both compile without errors and produce the documented behaviour in their respective lab environments.
  Pass if     : Both variants render correctly, their respective cache behaviour is observable (e.g., stale data served for cached variant, fresh data for uncached), and the migration notes in the challenge spec are accurate.
  Fail if     : Either variant fails to build, throws a runtime error, or the observable cache behaviour contradicts the teaching notes.
  Automatable : partial (build check automatable; behaviour verification requires a controlled data-mutation sequence)
  @functional

## Scaffold Integrity — Starters, Solutions, and Defend-It Artifacts

🟡 Every challenge's starter scaffold compiles without errors
  Scenario    : For each of the ~20 challenges in /labs, run `tsc --noEmit` and `next build` (or equivalent) against the starter directory in isolation.
  Pass if     : All starters exit build/typecheck with 0 errors. Deliberate incomplete stubs (marked TODO/placeholder) are permitted only if they do not produce compile errors.
  Fail if     : Any starter produces a TypeScript error, a missing-module error, or a build failure that is not a documented intentional stub.
  Automatable : yes (scripted loop over labs/*/starter)
  @functional

🟡 Reference solutions are stored separately from starters and are not exposed in the starter scaffold
  Scenario    : Inspect the file tree of each challenge. Verify that the reference solution files are not present inside the starter directory, and that the starter contains no import paths that resolve to solution files.
  Pass if     : For all challenges: solution files exist only in a separate /solution or equivalent directory that is excluded from the starter; no starter file imports from the solution path.
  Fail if     : Any challenge's starter directory contains solution files, or any starter-file import path resolves to a solution file.
  Automatable : yes (file-tree and import-path grep)
  @functional

🟡 Every challenge has a committed Defend-It artifact with model answers
  Scenario    : For each challenge in /labs, check that a Defend-It file (e.g. defend-it.md or equivalent) exists at the expected path, contains at least one question, and contains a model answer section.
  Pass if     : All ~20 challenges have the Defend-It file present, non-empty, with both question and model-answer content.
  Fail if     : Any challenge is missing the Defend-It file, or the file exists but contains no model answers (only prompts with empty answer sections).
  Automatable : yes (file existence + content grep)
  @functional

🟡 Every challenge has acceptance criteria committed alongside its spec
  Scenario    : For each challenge in /labs, check that a spec file (e.g. SPEC.md or spec.ts) exists and contains a non-empty acceptance criteria section.
  Pass if     : All challenges have a spec file with at least one testable acceptance criterion.
  Fail if     : Any challenge is missing its spec, or the spec exists but has no acceptance criteria content.
  Automatable : yes (file existence + content grep)
  @functional

🟡 Each challenge's reference solution meets its own documented acceptance criteria
  Scenario    : For each challenge in /labs, run the acceptance criteria checks against the reference solution (not the starter). For challenges that include automated tests, run those tests. For challenges with manual criteria, verify against the spec checklist.
  Pass if     : All acceptance criteria listed in each challenge's spec are met by that challenge's reference solution.
  Fail if     : Any reference solution fails one or more of its own acceptance criteria, or the acceptance criteria cannot be evaluated because they are too vague.
  Automatable : partial (automated criteria can be scripted; manual criteria require human review)
  @functional

## Core App Flows — E2E Coverage

🟡 The storefront product listing page renders and is navigable
  Scenario    : Load the Nextmart storefront home or product listing route. Verify products are listed and each product is navigable.
  Pass if     : Products render, at least one product is clickable and navigates to a product detail page.
  Fail if     : Page renders blank, throws a runtime error, or product links are broken.
  Automatable : yes (Playwright)
  @functional

🟡 Cart add, persist, and login-reconciliation flow works end to end
  Scenario    : Add items to the cart as an unauthenticated user (guest cart). Log in with a test account that already has items in its saved cart. Verify that the guest cart and the saved cart are reconciled (merged or otherwise resolved per the documented strategy).
  Pass if     : After login, the cart reflects the reconciled state as described in the challenge spec. No items are silently dropped.
  Fail if     : Guest cart items are lost on login, or the reconciliation throws a runtime error, or the cart state is inconsistent (e.g., duplicated items where deduplication is expected).
  Automatable : yes (Playwright with two-state fixture: guest additions + pre-seeded server cart)
  @functional

🟡 Optimistic UI rolls back correctly when the server rejects the mutation
  Scenario    : Trigger an optimistic UI action (e.g., add-to-wishlist or a form submit) while the server is configured to return a failure response. Observe the UI before and after the server response.
  Pass if     : The UI immediately shows the optimistic state, then reverts to the pre-action state after receiving the server rejection. An appropriate error message is displayed.
  Fail if     : The UI stays in the optimistic state after server rejection (phantom update), or the rollback throws a React/hydration error.
  Automatable : yes (Playwright with network interception to force server rejection)
  @functional

🟡 URL-as-state filters are shareable and restorable from a direct URL load
  Scenario    : Apply one or more product filters that encode their state in the URL query string. Copy the resulting URL. Open it in a new tab (simulating a share).
  Pass if     : The new tab renders with the same filtered state as the original tab. The filter UI reflects the URL parameters.
  Fail if     : The shared URL renders an unfiltered page, or the filter UI shows a different state than the URL parameters specify.
  Automatable : yes (Playwright — navigate to URL directly, assert filter UI state)
  @functional

🟡 The seller dashboard is accessible to an authenticated seller and shows their data
  Scenario    : Log in as a test seller account. Navigate to the seller dashboard route.
  Pass if     : The dashboard renders with the seller's data (orders, listings, or equivalent).
  Fail if     : Dashboard returns 403/404, renders blank, or shows another seller's data.
  Automatable : yes (Playwright)
  @functional

## Rendering Strategies — Correctness Verification

🟡 SSG pages are prerendered at build time and served as static HTML
  Scenario    : After `next build`, inspect the .next/server/ output for the designated SSG routes. Verify that a static HTML file exists for each SSG page.
  Pass if     : Static HTML files are present for all documented SSG routes. The pages serve with no server-side computation on request (confirmed by cache headers or build manifest).
  Fail if     : SSG pages are absent from the build output, or serve with server-rendering indicators (no-store headers, dynamic responses) when they should be static.
  Automatable : yes (build output inspection + HTTP response header check)
  @functional

🟡 The deliberate CSR widget is client-rendered and not present in the initial SSR HTML
  Scenario    : Load the page containing the designated CSR widget. Inspect the initial HTTP response HTML (before hydration).
  Pass if     : The CSR widget content is absent from the initial HTML source (it appears only after JavaScript execution).
  Fail if     : The CSR widget content is present in the initial HTML, indicating unintended SSR.
  Automatable : partial (Playwright can capture pre-hydration HTML; requires knowing the exact element selector for the CSR widget)
  @functional

🟡 TanStack Query hydration boundary produces no client/server mismatch errors
  Scenario    : Load the page that uses TanStack Query with a server-prefetched hydration boundary. Observe the browser console.
  Pass if     : No hydration mismatch warnings or errors appear in the console. The page renders correctly.
  Fail if     : Any "Text content does not match server-rendered HTML" or React hydration error appears.
  Automatable : yes (Playwright with console error listener)
  @functional

🟡 ISR revalidation serves stale content and then updates within the declared revalidation window
  Scenario    : Load an ISR page, record the rendered value. Trigger a data change in the backing store. Wait for the ISR revalidation period to pass (or force-trigger via on-demand revalidation if configured). Reload the page.
  Pass if     : The page initially serves stale content (expected ISR behaviour), and after the revalidation window the updated content is served.
  Fail if     : The page never updates after data changes (broken invalidation), or always fetches fresh data on every request (not actually ISR).
  Automatable : partial (time-dependent; automatable with a short revalidation window in the test fixture)
  @functional

  @functional

🟡 sitemap.xml is present and contains at least the expected static routes
  Scenario    : Request /sitemap.xml from the running app.
  Pass if     : HTTP 200, valid XML, and the sitemap contains entries for the documented static routes (home, product listing, at minimum).
  Fail if     : 404, malformed XML, or the sitemap is empty.
  Automatable : yes
  @functional

🟡 robots.txt is present and has expected directives
  Scenario    : Request /robots.txt from the running app.
  Pass if     : HTTP 200, valid robots.txt content with at least one User-agent and Disallow/Allow rule.
  Fail if     : 404 or empty response.
  Automatable : yes
  @functional

## Performance and Bundle (Non-blocker)

🟢 next/image usage does not introduce visible CLS on the product listing page
  Scenario    : Load the product listing page and observe layout shift. Reference the Cumulative Layout Shift (CLS) metric.
  Pass if     : CLS score is below 0.1 (Good threshold per Web Vitals).
  Automatable : partial (Playwright with lighthouse plugin or web-vitals instrumentation)
  @non-blocker

🟢 Client bundle size delta for the RSC boundary challenge is within an acceptable range
  Scenario    : Compare the client JS bundle size for the RSC boundary challenge route before and after introducing the RSC/client boundary. Record the delta.
  Pass if     : The client bundle does not grow unexpectedly; the delta is documented in the challenge notes as a teaching point.
  Automatable : partial (next build + bundle analyzer)
  @non-blocker

🟢 Lighthouse performance score on the storefront home page meets a documented baseline
  Scenario    : Run Lighthouse on the storefront home page in production build mode.
  Pass if     : Performance score is documented. No regression from the baseline recorded in the project's performance budget (if one is defined).
  Automatable : partial (CI Lighthouse action)
  @non-blocker

🟢 Edge runtime route handler cold-start time is observed and documented
  Scenario    : Send the first request to the edge-runtime Route Handler (C13) after a cold start. Record the response time.
  Pass if     : Cold-start time is recorded and documented in the challenge notes. No hard threshold — this is an observation exercise.
  Automatable : partial (timed curl or fetch; requires deployment to an edge environment)
  @non-blocker

🟢 Prefetch behaviour on the product listing page is observable and matches documented expectation
  Scenario    : Hover or viewport-intersect a product card link. Observe network tab for prefetch requests.
  Pass if     : A prefetch request is fired for the product detail route as documented in the lab notes.
  Automatable : partial (Playwright network interception)
  @non-blocker

🟢 Code-splitting verification — the RSC boundary challenge client chunk is separate from the server chunk
  Scenario    : Inspect the .next/static/chunks/ output after build for the RSC boundary challenge route. Confirm that client-only code is in a separate chunk from the server output.
  Pass if     : Separate chunk files exist for client and server portions as expected by the teaching material.
  Automatable : partial (build output file inspection)
  @non-blocker

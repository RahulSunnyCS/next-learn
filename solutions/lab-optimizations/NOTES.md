# Design & Implementation Notes — Built-in Optimizations Lab

This file documents every non-obvious decision made in this challenge's
implementation.  It is the reference a reviewer or future maintainer should
read alongside the code.

---

## 1. Why SVG images instead of PNG/JPEG

The task requires placing sample images under `_components/assets/` and using
static imports.  SVGs were chosen because:

- They are tiny text files (~500 bytes each vs. potentially 50+ kB for a
  realistic photograph) — the repo stays lightweight.
- Next.js handles SVG static imports the same as raster images for the
  purposes of the width/height auto-extraction demo.
- No binary blobs committed to git — reviewers can read and verify the
  asset files directly.

In a production scenario the same pattern works identically with `.jpg`,
`.png`, or `.webp` files — swap the SVG imports for raster imports without
changing any other code.

---

## 2. Why `placeholder="blur"` works on SVGs

SVG files imported as StaticImageData have a `blurDataURL` auto-generated by
Next.js's image optimisation pipeline (it creates a tiny base64-encoded JPEG
thumbnail from the SVG rasterised at 8×8 pixels).  So `placeholder="blur"`
works without any extra `blurDataURL` prop for static imports — including SVG
static imports.

For **remote** images (the `RemoteImageWithSizes` example), `blurDataURL` MUST
be provided manually because Next.js cannot know the image contents at build
time.  The example uses a pre-generated base64 JPEG thumbnail.

## 3. Why the font is in a local `layout.tsx` (not `app/layout.tsx`)

The task explicitly asks to "scope [the font] to your challenge subtree."
Using a local layout demonstrates the recommended pattern for per-section
fonts (e.g. a display font only on a landing page).

If this font were added to `app/layout.tsx`, it would:
- Apply to every challenge route, potentially overriding their intended
  typography.
- Be forbidden by the task contract (`app/layout.tsx` is in `files_forbidden`).

The CSS variable approach (`variable: "--font-lab"`) was chosen over
`className` because it allows opt-in usage: any element in the subtree can
apply the font by writing `font-family: var(--font-lab)`.  Elements that don't
set this property use the body's system-ui font as normal.

## 4. `beforeInteractive` — shown as code sample, not live

`strategy="beforeInteractive"` on a `<Script>` inside a nested component is
either silently ignored or produces a Next.js warning in v16.  It only works
in a `layout.tsx` or `page.tsx` file.

Rendering a live `beforeInteractive` script in `ScriptDemo.tsx` would be
misleading — learners would see no observable difference and think it is
equivalent to `afterInteractive`.  The decision was to show it as a code
sample with an explicit note explaining the placement constraint.

## 5. Why `next/dynamic` is called at module level

```tsx
// CORRECT — module level
const HeavyChart = dynamic(() => import("..."));

// WRONG — inside a component
function Page() {
  const HeavyChart = dynamic(() => import("...")); // re-creates on every render
}
```

Calling `next/dynamic` inside a component function creates a new dynamic
wrapper on every render.  This defeats React's reconciliation (the component
identity changes, causing unnecessary unmounts/remounts) and prevents the
build-time chunk-splitting from working correctly (Webpack/Turbopack performs
code splitting at the module analysis phase, not at runtime).

The import path must also be a static string literal (not a variable) so the
bundler can trace it at build time.

## 6. Why `ssr: false` on HeavyAnalyticsChart

The chart component uses browser APIs (`useState`, event handlers, DOM
measurements in a real charting library).  Setting `ssr: false`:

1. Avoids Node.js crashes when the server tries to render `window`/`document`
   references.
2. Prevents React hydration mismatches (server HTML would not match client
   HTML because chart dimensions depend on viewport size, unknown during SSR).
3. Keeps the server-side bundle clean — the chart JS is never imported by
   the Node.js server process.

The downside is that the chart is invisible in the initial HTML (server sends
only the loading skeleton).  This is acceptable because:
- Charts are typically below the fold (not LCP candidates).
- Charts require interactivity anyway — search engines get nothing useful from
  a static chart screenshot.

## 7. Why catalog data is inside `<Suspense>` on the lab page

Cache Components rule: any uncached or dynamic data read MUST be inside a
`<Suspense>` boundary, or the build fails with "Uncached data was accessed
outside of `<Suspense>`".

`getFeaturedProducts()` calls `listProducts()` from `lib/data/repository.ts`,
which is wrapped in `'use cache'` — but we still wrap it in Suspense because:
1. It is still an async read that streams in.
2. Keeps the page shell fully static (○ Static or ◐ Partial Prerender in
   the route table) — good for initial render performance.
3. Follows the canonical pattern from c01-auth so learners see consistency
   across challenges.

## 8. `sizes` prop on the remote image

The `sizes` prop in `RemoteImageWithSizes`:
```tsx
sizes="(max-width: 768px) 100vw, 50vw"
```

This tells the browser: on screens narrower than 768px, the image will fill
100% of the viewport width; on wider screens, it will be 50% of viewport width.

Without `sizes`, the browser assumes the image takes up 100vw at all times
and downloads the full-width variant even on mobile.  A phone gets a 1200px
wide image when it only needed a 390px wide one.  Setting `sizes` lets the
browser pick the correct entry from the `srcset` — typically 2–4x smaller
on mobile, a meaningful bandwidth saving.

---

## 9. `blurDataURL` value in `RemoteImageWithSizes`

The `blurDataURL` is a 10-pixel-wide base64-encoded JPEG that acts as a
coloured placeholder.  In production you would generate this with a tool like
`plaiceholder` at build time (run as part of a content ingestion pipeline)
or store it in your CMS/database alongside the image URL.

The specific value in the example was hand-crafted to be a valid JPEG data URI
in the minimum number of bytes — it renders as a neutral warm-grey colour.
For a real product image you would use a colour-accurate placeholder derived
from the actual image content.

---

## 10. No new npm dependencies

The task contract forbids adding to `package.json`.  Every pattern implemented
here uses only APIs that ship with Next.js:
- `next/image` (built-in)
- `next/font/google` (built-in, downloads fonts at build time)
- `next/script` (built-in)
- `next/link` (built-in)
- `next/dynamic` (built-in)
- `next/cache` (`cacheLife` for the 'use cache' function)

This is also a teaching point: for common optimisation needs, you don't need
a third-party library — the framework handles it.
